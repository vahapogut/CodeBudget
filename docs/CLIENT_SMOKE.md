# Actual client MCP smoke without a model

Run `pnpm build`, then `pnpm smoke:clients` with an installed Codex CLI. The result is saved to [client-smoke-result.json](client-smoke-result.json). This check has no paid model connector and starts no conversation or turn. The Claude Code counterpart is `pnpm smoke:claude-mcp`, described below.

On 2026-09-30 on Linux with Node v22.22.2 and Codex CLI 0.139.0 (installed from the npm registry into a temporary directory), the actual Codex app-server connected to CodeBudget and discovered the `get_changes`, `prepare_context` and `read_evidence` tool schemas; server metadata identified `codebudget` version `0.1.0-beta.3`. The registration was an explicit launch without `--root`, so this also shows that Codex starts project MCP servers inside the project and that the server finds the project from its working directory. The earlier run on Windows with Node 22.16.0 identified version `0.1.0-beta.1`. The local stdio server requires no account authentication; the client's `authStatus: unsupported` means this transport has no OAuth authentication mechanism, not a failed connection.

The script creates a temporary project and a separate temporary `CODEX_HOME` for child processes. It runs the built CodeBudget CLI's observe-mode initialization and project-local Codex adapter installation, trusts only that temporary project, and disables analytics/feedback in the temporary client configuration. Only operating-system process variables are inherited; existing account credentials and user client configuration are not supplied. The parent environment and global settings are unchanged. Temporary files and the app-server are cleaned up after the check.

Before connecting, the installed client generates its own protocol JSON Schema. The script checks that its two request methods are supported, then sends exactly `initialize`, the `initialized` notification, and `mcpServerStatus/list`. It verifies the live inventory and each tool's object input schema. It sends no `thread/start`, `turn/start`, account or login request. Codex warnings about declining to create PATH helper aliases under the temporary directory and about using its bundled sandbox helper are retained with normalized paths; they did not prevent the connection.

This proves the installed Codex client's project registration and MCP inventory handshake. The script does not call the tools through Codex, execute a model session, measure client prompt replacement, capture provider usage, or establish task quality or token savings. Tool execution itself is covered separately by the MCP SDK and installed-package protocol smoke tests. Actual Cursor and Antigravity clients are outside this script's measured coverage. Reference-solution task tests remain local evaluator checks; real-model pilot experiments remain unrun.

## Claude Code health check

`pnpm smoke:claude-mcp` runs the installed Claude Code client with an empty temporary `CLAUDE_CONFIG_DIR` and home, telemetry, auto-update and non-essential traffic disabled, and only operating-system process variables. It registers CodeBudget in that temporary local scope with an explicit launch without `--root`, then runs `claude mcp list` and `claude mcp get codebudget`. The check requires that the client lists exactly one server, the temporary CodeBudget registration, and reports it as connected. The result is written to `dist/claude-client-smoke-result.json`, or to [claude-client-smoke-result.json](claude-client-smoke-result.json) with `--record`.

On 2026-09-30 on Linux with Node v22.22.2 and Claude Code 2.1.286, the client listed only CodeBudget and reported it as connected. In a manual run of the same procedure with the same client, its MCP log recorded the stdio connection with the server identity `codebudget 0.1.0-beta.3` and tool capability. No prompt, login, approval choice or model request was submitted, and nothing outside the temporary directory changed. The CI `plugin-contract` job runs the same check against the newest published client on every push.

This health check covers the client starting the server, the initialize handshake and the advertised capabilities. It does not list or call tools inside a model session, run the plugin hooks, or establish model-visible output replacement; the separate [model acceptance](MODEL_ACCEPTANCE.md) sessions cover those.
